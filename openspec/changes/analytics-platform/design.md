# Design: analytics-platform

## Context

Ouroboros (main) is a two-service stack on the rancherlocal k3s cluster, deployed by Argo CD from `deploy/apps/ouroboros` in this repo: `ouroboros/api` (FastAPI ingestion, dev-mode RS256 JWT auth) and `ouroboros/reporting` (FastAPI read side that also serves the Vite SPA from `STATIC_DIR`), on CloudNativePG Postgres 17 `ouroboros-db`. One hostname, `https://ouroboros.rancherlocal.azure.example.com`: `/v1/telemetry/*` reaches the API with its own bearer auth; everything else sits behind Envoy Gateway + oauth2-proxy Google login, which forwards `X-Auth-Request-Email`. Single user today, team-shaped tomorrow, cheapest possible footprint, no secrets in Git.

The data model is one table, `events`, written only when a skill self-reports through `python3 -m ouroboros_client.report`. The plugin's two hooks (`UserPromptSubmit`, `Stop`) keep a local ring of prompt/response pairs that ride along on the next outcome event. The reporting API is unauthenticated inside the Gateway and the dashboard is three recharts views.

Claude Code now exposes far richer signals: 33 hook events with `transcript_path`, `cwd`, tool metadata and durations, subagent and compaction lifecycle, `InstructionsLoaded` (which CLAUDE.md/rules file was loaded and why), model switches; a built-in OpenTelemetry exporter with per-model token and USD cost metrics attributed to `skill.name` / `plugin.name` / `agent.name`, and events for `skill_activated`, `compaction` (pre/post tokens), `subagent_completed`, `api_request`; and plaintext transcripts under `~/.claude/projects/`. The UI target (revised 2026-11-08) is **shadcn/ui**: Vercel acquired Tremor in January 2025 and its cofounder has said net-new development happens in shadcn/ui; Tremor Raw has had no release since early 2025 and its React 19 PR has sat unreviewed since June 2026. shadcn/ui is actively maintained, built on Tailwind + Recharts over headless primitives (Base UI by default in the current CLI, Radix as the legacy option — see D1), and ships chart components and dashboard blocks; Tremor's Dashboard template stays useful as a layout reference and individual Tremor Raw files can still be borrowed.

The standing goal: collect usage, prompts and context so an autonomous loop can improve agents, skills, context and hooks while minimizing context bloat. Privacy posture: verbatim text is sensitive, telemetry is disclosed and never covert, `OUROBOROS_TELEMETRY=off` is absolute.

## Goals / Non-Goals

**Goals:**
- Leadership can answer, from one page with a date range and period comparison: who uses Claude Code and which skills/agents, how often outcomes succeed or get corrected, what it costs, how sentiment trends, and how much context we pay for always-on artifacts.
- Engineers can drill from an aggregate to the sessions, turns, tool calls, compactions and loaded instructions behind it, inspect prompts and context with the right role, and export structured data (NDJSON/Parquet) for modeling.
- Every artifact the loop can improve — skill, hook, agent, CLAUDE.md/rules file — is a first-class, versioned entity with a measured always-on token cost and attributable outcomes.
- The loop's own work is data: proposals, their evidence, approvals, the PR that applied them, and before/after metrics.
- Collection is layered: structure and content from hooks (metadata by default), usage and cost from OTel, transcripts only by explicit opt-in. All of it joins on `session_id` and `prompt_id`.
- Zero regression on the hook path: stdlib-only, no network, always exit 0.
- Two images, one database, one hostname, Argo CD-managed, no secrets in Git.

**Non-Goals:**
- Entra ID auth for ingestion (`AUTH_MODE=entra` stays reserved; the design must not block it).
- Autonomous application of proposals; v1 is human-approved only.
- LLM-based sentiment/theme scoring and embeddings search (listed as later, optional jobs).
- Replacing Claude Code's own OTel pipeline with a custom SDK, or running a general-purpose OTel collector.
- Multi-tenancy beyond one Google Workspace / one Entra tenant.

## Decisions

### D1: shadcn/ui is the design system, in the existing Vite SPA; Tremor is a borrowed-component source and a layout reference
Adopt **shadcn/ui** (MIT; copy-into-source components over headless primitives — Base UI, see the spike result — and Tailwind, installed with `npx shadcn@latest init` / `add`) as the dashboard's design system. Verified 2026-11-08: its CLI has a first-class Vite path (<https://ui.shadcn.com/docs/installation/vite>), its `chart` component wraps Recharts (<https://ui.shadcn.com/docs/components/chart>), its data table is built on TanStack Table (<https://ui.shadcn.com/docs/components/data-table>), and its blocks catalogue ships `dashboard-01` (inset sidebar, `section-cards.tsx` KPI cards, `chart-area-interactive.tsx`, `data-table.tsx`) plus the `sidebar-03`/`sidebar-07` shells (<https://ui.shadcn.com/blocks>). Every component lands as source under `dashboard/src/components/ui/` and is owned by us. The **Tremor Dashboard template** (`tremorlabs/template-dashboard`, MIT) remains the *layout reference* for the Leadership experience — overview KPIs with period comparison, a details table, settings pages — but none of its code is copied as-is. **Tremor Raw** components (`tremorlabs/tremor`, Apache-2.0) may be *borrowed file by file* where shadcn/ui has no equivalent (BarList, Tracker, CategoryBar, ProgressBar, ProgressCircle; DonutChart/SparkChart only if the spike shows a cheap port), vendored per D3. We do **not** adopt Next.js: nothing needs a server; keeping the Vite SPA preserves FastAPI static serving, the same-origin `/v1` API and the one-hostname Gateway setup.

Spike result (0.3): the current shadcn CLI (4.23) defaults to style `base-nova` on **Base UI** (`@base-ui/react`) primitives rather than Radix; `init -b radix` is now the legacy path and the `new-york` style name no longer exists. We accept Base UI as the primitive layer: it is what the blocks catalogue targets, and the only API differences are composition through the `render` prop instead of `asChild` (`<SidebarMenuButton render={<NavLink to=… />}>`), `Select` taking an `items` map for `SelectValue` labels, and `onValueChange` callbacks receiving `(value, eventDetails)`. Tremor Raw **BarList** is vendored under `dashboard/src/components/charts/tremor/` with Tremor's Apache-2.0 `LICENSE` and a `NOTICE` (source path, commit, modifications); the port was trivial (`forwardRef` → `ref` prop, `cx` → `cn`, Tremor classes → shadcn tokens) and involves no Recharts. `DonutChart` was read and **not** vendored: it targets Recharts 2 and re-implements what shadcn's `chart.tsx` provides, and the equivalent donut is ~40 lines as a shadcn chart config, so the Recharts-based Tremor charts (DonutChart, SparkChart) are rebuilt as chart configs and only the non-Recharts files (BarList, Tracker, CategoryBar, ProgressBar, ProgressCircle) are borrowed.

Alternatives rejected: **Tremor Raw as the primary system** (upstream effectively frozen since early 2025; we would carry every React, Recharts and Tailwind upgrade alone); **classic `@tremor/react`** (3.18.x npm package, Tailwind 3 only, unmaintained, cannot be fixed locally); **the Tremor Dashboard template as-is** (Next.js, Tailwind 3.4, an old Tremor Raw snapshot — three migrations at once with no upstream); **hand-rolled CSS / recharts-only views** (no design system, no table, filter or date primitives, does not meet the leadership bar).

### D2: Tailwind v4 via `shadcn init` in the existing Vite SPA
`dashboard/` stays a Vite SPA. Tailwind **v4** is added exactly as shadcn's Vite guide prescribes: `tailwindcss` + `@tailwindcss/vite`, `@import "tailwindcss";` in the stylesheet (`dashboard/src/index.css`, the file `shadcn init` writes), the `@/*` path alias in `tsconfig.json` and `vite.config.ts`, then `npx shadcn@latest init` (style `base-nova`, the CLI's current default — the design originally named `new-york`, which the CLI no longer offers; CSS variables on, `tw-animate-css` instead of the deprecated `tailwindcss-animate`; <https://ui.shadcn.com/docs/tailwind-v4>). Theme tokens are `:root` / `.dark` CSS variables exposed through `@theme inline`; dark mode uses the class strategy (`@custom-variant dark (&:is(.dark *))`) driven by a small theme toggle, so it works without `prefers-color-scheme`. Borrowed Tremor Raw files already target Tailwind v4; the template's v3.4 classes are never copied, only its layout. `dashboard/src/theme.ts` and the hand-written `dashboard/src/styles.css` are removed. Alternatives rejected: Tailwind v3.4 (shadcn still runs on it, but new shadcn projects and blocks default to v4, so v3 would be a second migration later); plain CSS modules (makes neither shadcn/ui nor Tremor usable).

Spike result (0.3): the setup works as written (Tailwind 4.3 via `@tailwindcss/vite`, class-strategy dark mode with a pre-paint script in `index.html`, `localStorage` key `ouroboros-theme`). `init` also adds runtime dependencies the design did not list: `shadcn` itself (for `@import "shadcn/tailwind.css"`), `cn` (replaces `clsx` + `tailwind-merge`; components import `from "cn"`), `@fontsource-variable/geist` (76 KB of fonts in `dist/`; drop in Phase 4 if the system font stack is preferred) and `tw-animate-css`. The `base-nova` neutral preset ships a grayscale `--chart-1..5`, so the dataviz palette plus `--status-good/warn/crit` and `--chart-previous` are written over it in the stylesheet (`:root` / `.dark`, exposed through `@theme inline`).

### D3: Charts are shadcn/ui chart components on Recharts 3, on React 19; Tremor Raw charts vendored only where needed
shadcn/ui's `chart` component "now uses Recharts v3" and documents the v2→v3 upgrade (<https://ui.shadcn.com/docs/components/chart>); `recharts@3.10.1` declares peer `react ^16.8.0 || ^17.0.0 || ^18.0.0 || ^19.0.0` (its published `package.json`). shadcn's docs state that new projects start with **Tailwind v4 and React 19** while existing Tailwind v3 / React 18 apps "still work" (<https://ui.shadcn.com/docs/tailwind-v4>, <https://ui.shadcn.com/docs/react-19>). Because the dashboard is being rebuilt rather than extended, pin to what `shadcn init` produces today: **React 19.x** (`@types/react` 19), **Recharts 3.x**, with `react-is` installed at the matching major because recharts lists it as a peer. Charts are composed from `ChartContainer` / `ChartTooltip` / `ChartLegend` with a `ChartConfig` per chart and the `var(--chart-1..5)` palette, so every Leadership overview, outcomes, cost and trend chart is a shadcn chart. Tremor Raw files borrowed where shadcn/ui has no equivalent are vendored under `dashboard/src/components/charts/tremor/` together with Tremor's Apache-2.0 `LICENSE` and a `NOTICE` naming the source repository, file paths and commit; the non-Recharts ones (BarList, Tracker, CategoryBar, ProgressBar, ProgressCircle) port as-is, while the Recharts-based ones (DonutChart, SparkChart) are written against Recharts 2 and are vendored only if spike 0.3 shows the port to the v3 API is small — otherwise they are rebuilt as shadcn chart configs. Alternatives rejected: Recharts 2.x + React 18 (what the current dashboard and Tremor Raw use; would mean installing shadcn charts from an older snapshot and migrating twice); other chart libraries (visx, nivo, ECharts — no shadcn integration, loses `ChartConfig` theming). Mitigation for the React 19 peer-dependency friction shadcn documents: use `--legacy-peer-deps` only for a named package, never project-wide, and record each one in `dashboard/package.json` `overrides`.

Spike result (0.3): pins are **React 19.3** (`@types/react` 19.3, `react-is` 19.3 pinned exactly), **Recharts 3.10**, **Tailwind 4.3** via `@tailwindcss/vite`, **react-router-dom 7**, **react-day-picker 10** with date-fns 4, Vite 7 (Vite 8 and `@vitejs/plugin-react` 6 are Rolldown-based and deliberately deferred). No `--legacy-peer-deps` was needed on npm 10.8, so the `overrides` mitigation stays unused. DonutChart/SparkChart are rebuilt as chart configs (D1). **Cost**: the migrated main chunk is **~335 KB gzipped vs ~156 KB before** (Recharts 3 ≈ 27 % of the chunk — it now bundles `@reduxjs/toolkit`, `immer`, `es-toolkit`, `decimal.js-light` — react-dom 21 %, Base UI ≈ 17 %, react-day-picker 5 %), and Vite's 500 KB chunk warning fires. Phase 4 therefore carries a **bundle budget** (task 4.14): `lazy()` route modules so Recharts and react-day-picker load only on the pages that use them, a target of ≤ 250 KB gzipped for the initial route, and a CI check that fails when the gzipped main chunk exceeds 400 KB; measure with `rollup-plugin-visualizer` (source-map-explorer rejects Vite 7 source maps). **Implementation notes**: `shadcn add` rewrote the `recharts` range to `^3.8.0` and left `package.json` out of sync with the lockfile, which broke `npm ci` in the Dockerfile — run `npm install` after every `shadcn add` and verify with `npm ci` in a scratch copy; Recharts 3 typings are stricter (`Tooltip formatter` value may be `undefined`, `labelFormatter` label is `ReactNode`); use `var(--chart-n)` not `hsl(var(--chart-n))`; no `layout` on `<Bar>` when `<BarChart layout>` is set; give `ChartContainer` an explicit height class or `ResponsiveContainer` cannot measure.

### D4: Routing, URL-held filter state, and two personas
`react-router-dom` 7 (the v6 API; the `v7_*` future flags are defaults) with routes `/overview` (Leadership), `/engineering/*` (Engineering workspace: `artifacts`, `artifacts/:id`, `failures`, `sessions`, `sessions/:id`, `inspector`, `export`), `/proposals`, `/settings/*`. The filterbar (date range, comparison period, skill/agent/user selectors) writes to URL search params so views are linkable and shareable; a tiny `useFilters()` hook over `useSearchParams` handles this (no `nuqs`, which the Tremor template uses under Next.js). Persona is a role-driven landing page, not a separate app: `leadership` lands on `/overview` and sees redacted detail pages; `engineer` lands on `/engineering`; `admin` adds `/settings/users`. Alternative rejected: two SPAs or a persona switch stored in localStorage — duplicates layout and makes redaction a client concern (it must be server-side, D12).

Spike result (0.3): the layout-route shell and `useFilters()` over URL search params work as designed (`replace: true` on filter edits so the back button steps between pages, presets derived from the range). Deep links and refresh return 404 from `StaticFiles(html=True)`, which has no SPA fallback: task 4.12 (fallback route in `reporting/app/main.py`, plus the `.woff2` MIME type python-slim lacks) must land before any router-based page merges.

Implemented (Phase 4, `dashboard/src/`, `reporting/app/main.py`): routes `/overview`, `/engineering/{artifacts,artifacts/:id,failures,sessions,sessions/:id,inspector,export}`, `/proposals`, `/proposals/:id`, `/settings/{general,users}`; `/` redirects to `/v1/me`'s `landing` (leadership `/overview`, engineer and admin `/engineering` → `artifacts`), the sidebar shows only pages the role can use (Export engineer+, Users admin), and `/v1/me` 401/403 render dedicated pages. Leadership can open the engineering detail pages; the server redacts and `SensitiveText` renders each `{"redacted": true, "length": n}` marker as a muted "redacted (n chars)" chip. Filters live in URL search params through `lib/use-filters.ts` (`from`, `to`, `compare=previous|none`, `bucket=day|week`, `skill`, `agent`, `user`; `replace: true`), and the sidebar carries them between pages. Every route module is `lazy()` (including `/overview`) and `vite.config.ts` splits `vendor` (React, router, Base UI), `recharts`, `calendar` (react-day-picker + date-fns) and `table` (TanStack) chunks: the initial JS went from **326.7 KB gz** (spike build, one chunk; Vite reports 335 KB at its default gzip level) to **186.9 KB gz** (entry 23.8 + vendor 163.0) plus 15.7 KB gz CSS; `scripts/check-bundle.mjs` (run by `npm run build`, hence by the Dockerfile and the CI `dashboard` job) fails above 400 KB and warns above 250 KB; `npm run analyze` writes the `rollup-plugin-visualizer` treemap. **Font decision: system stack, Geist dropped** (`@fontsource-variable/geist` removed, 76 KB of `.woff2` no longer shipped; the UI is dense tabular data where the system sans reads well and renders without a font swap). The `.woff2` → `font/woff2` MIME entry stays for any future font. SPA serving: `/assets/*` is a plain `StaticFiles` mount (a missing hashed asset is a 404, never `index.html`), other existing files are served as-is, and any other GET returns `index.html` with `Cache-Control: no-cache`; `v1/`, `internal/`, `healthz`, `readyz` are never shadowed (unknown API paths stay 404 behind the auth middleware). `/proposals` and the artifact detail's proposals card call the D14 client and show the "improvement loop lands in Phase 5" empty state on the 404. Deviations: the stylesheet is `src/index.css` (what `shadcn init` writes), not `styles.css`; status colours split into fixed fills (`--status-*`, chart marks) and text-safe ink (`--status-*-text`, the `text-status-*` utilities, ≥ 4.5:1 per mode); there is no session-list endpoint, so `/engineering/sessions` merges the costliest sessions from `/v1/analytics/cost` with the sessions scored by `/v1/reports/sentiment` (stopgap, stated on the page); the failures drill-down to events filters `error_code` client-side over one page of `/v1/reports/events`, which has no `error_code` parameter. Verified by `dashboard/e2e/smoke.spec.ts` (Playwright) against the built image. Phase 5 closed both stopgaps: `GET /v1/analytics/sessions` (paginated, ordered by start, cost, turns, corrections or tokens, `q` on session-id prefix or project) backs `/engineering/sessions`, `/v1/reports/events` takes `error_code` so the drill-down filters server-side, and `/v1/analytics/outcomes` adds `current.tools` (calls, success, failure, interrupted per tool) for the failures page.

### D5: Two complementary collection pipelines — expanded hooks and built-in OTel
Collection splits by what each source is uniquely good at:

| Need | Hooks | OTel |
|---|---|---|
| Structure (session → prompt → tool calls → subagents → compaction) with `prompt_id`, `cwd`, `transcript_path`, `permission_mode`, `effort` | yes | partial |
| Content (prompt text, corrections, tool error text) — sensitive, opt-in per class | yes | only with `OTEL_LOG_*` flags, coarser |
| Which CLAUDE.md/rules/skill files were loaded and why (`InstructionsLoaded`, `UserPromptExpansion`) | yes | no |
| Tokens, USD cost, per-model, per `skill.name`/`agent.name`/`plugin.name` attribution, `api_request`, `compaction` pre/post tokens, `subagent_completed` totals | no | yes |
| Model-invoked skill activation (`skill_activated`) | unverified (no dedicated hook) | yes |

Both are therefore required. **Join keys**: `session_id` (present in every hook payload and as an OTel resource/log attribute) and `prompt_id` (hook `prompt_id` ↔ OTel `prompt.id`); `agent_id` links `SubagentStart/Stop` to `subagent_completed`. The server reconciles into `sessions`/`turns` (D9), tolerating either side arriving first. **Privacy toggle defaults** (written by `python3 -m ouroboros_client.setup_otel`, documented in disclosure): `OTEL_LOG_USER_PROMPTS=0`, `OTEL_LOG_ASSISTANT_RESPONSES=0`, `OTEL_LOG_TOOL_CONTENT=0`, `OTEL_LOG_RAW_API_BODIES=0`; `OTEL_LOG_TOOL_DETAILS=1` (needed for real skill/plugin names instead of `custom_skill`/`third-party`; it exposes names, not content). Prompt text continues to arrive only through the hook pipeline, where our own classification and redaction apply. Alternatives rejected: OTel only (no structure, no instruction-load signal, no prompt text under our control); hooks only (no token/cost data, no reliable skill attribution); parsing transcripts as the primary source (undocumented format, 30-day local retention, pulls full content by default — see D8).

Spike result (0.2): the OTel column is confirmed from real payloads (Claude Code 2.1.319). **Metrics observed**: `claude_code.session.count`, `claude_code.cost.usage`, `claude_code.token.usage`, `claude_code.active_time.total` — all delta sums with `asDouble` values, one data point per API request — with attributes `model`, `query_source`, `effort`, `type`, `skill.name` (on attributed points), `start_type`, plus the common set `session.id`, `user.id` (a stable 64-hex hash, not the UPN), `anthropic.provider`, `anthropic.custom_base_url` (leaks the configured base URL; **dropped on ingest**), `terminal.type`. **Log events observed**, in order for one turn: `managed_settings_resolved`, `hook_registered`, `plugin_loaded`, `user_prompt`, `hook_execution_start`, `hook_execution_complete`, `tool_decision`, `skill_activated`, `tool_result`, `api_request`, `assistant_response`. `prompt.id` is on every per-turn event but not on the startup events or on metric data points. **`OTEL_LOG_TOOL_DETAILS=1`** is what turns `custom_skill` / `third-party` into real skill, plugin and hook names on `skill_activated`, `plugin_loaded` and `hook_registered`, and it adds `tool_parameters` / `tool_input` (tool arguments, sensitive class — stored only under the content opt-in, otherwise dropped on ingest); `api_request` and the cost/token counters carry the real `skill.name` regardless of the flag. `tool_result.duration_ms` was negative for a Bash call, so **tool latency stays a hook-pipeline fact**. `query_source` is `sdk` on `api_request` but `main` on the metric points of the same `-p` run; treat them as one bucket. Not yet observed because nothing triggered them: `compaction`, `subagent_completed`, `api_error`, `api_refusal`, `tool_decision` with `reject`, `mcp_server_connection`; the OAuth-only identity attributes (`user.email`, `user.account_uuid`, `organization.id`) were absent in the API-key environment used.

Verified (0.4/2.11): the join keys hold - hook `prompt_id` == OTel `prompt.id` == transcript `promptId` in 4/4 turns, and hook `SubagentStart/Stop.agent_id` == OTel `subagent_completed.agent_id`. Model-invoked skill activation **is** visible to hooks as a `PostToolUse` with `tool_name: Skill` / `tool_input.skill`, so the last row of the table is "yes / yes" and `skill_activations` reconciles both sources on `(session_id, prompt_id, skill_name)`. Built-in local commands (`/model`, `/compact`) emit OTel `user_prompt` but no `UserPromptSubmit`/`Stop` hook, so a turn may exist on the OTel side only.

### D6: Hook events are metadata-first, spooled locally, uploaded in batches
`ouroboros-hook` becomes a dispatcher over `hook_event_name`. Per event it emits one **hook event** record `{hook_event_id, session_id, prompt_id?, agent_id?, hook_event_name, client_ts, cwd_hash, payload}` where `payload` is a whitelist projection, never the raw stdin:
- `SessionStart`: `source`, `model`, `agent_type`, `context_tokens`, `permission_mode`, `effort`, `session_title` (sensitive class). `SessionEnd`: `reason`.
- `UserPromptSubmit`: `prompt` (sensitive, goes to the local turn cache **and** the hook event only when `OUROBOROS_CAPTURE_PROMPTS=on`, default **on** because this is the existing disclosed behaviour), `prompt_length`.
- `UserPromptExpansion`: `expansion_type`, `command_name`, `command_source`, `command_args_length` (args text only with `OUROBOROS_CAPTURE_TOOL_CONTENT=on`).
- `PostToolUse` / `PostToolUseFailure` / `PostToolBatch`: `tool_name`, `tool_use_id`, `mcp_server`, `duration_ms`, `success`, `is_interrupt`, `input_bytes`, `output_bytes`, `error_class` (first line of `error`, truncated). `tool_input`/`tool_response` content only with `OUROBOROS_CAPTURE_TOOL_CONTENT=on` (default off). `PreToolUse` is not hooked (doubles event volume, adds nothing Post lacks except pre-decision timing).
- `SubagentStart` / `SubagentStop`: `agent_id`, `agent_type`, `agent_transcript_path` (hashed), `last_assistant_message` length (text only when prompts capture is on).
- `PreCompact` / `PostCompact`: `trigger`, `custom_instructions` length, `compact_summary` length (summary text only with `OUROBOROS_CAPTURE_PROMPTS=on`).
- `InstructionsLoaded`: `file_path` (relative to `cwd`, plus content hash computed locally when the file is readable), `memory_type`, `load_reason`, `globs`, `trigger_file_path`, `parent_file_path`.
- `PreModelSwitch` / `PostModelSwitch`: `from_model`, `to_model`, `context_tokens`.
- `Stop`: as today (completes the turn cache) plus `stop_hook_active`.
Records go to `~/.ouroboros/spool/hooks/` (same atomic-file spool, separate directory so stale-outcome logic does not apply) and are uploaded by the existing background sender to `POST /v1/telemetry/hook-events` in batches of ≤200 with the dev/Entra bearer token, `≤3s`, drop-oldest cap 5,000. The sender is nudged by any hook run and by `report`, so a session that never reports a skill outcome still uploads. The server stores the projected payload as JSONB alongside the normalized columns so later parser fixes can be replayed. `OUROBOROS_TELEMETRY=off` disables every event. Alternatives rejected: send from the hook process (adds network latency to each turn, violates D4 of the SDK change); capture everything and classify server-side (sensitive content would leave the machine before the user's toggle applies).

Verified (0.4): every event above fires in 2.1.319 and `client/tests/fixtures/hooks/` holds one redacted fixture per event. Field-level deviations the dispatcher must absorb: `SessionStart(startup)` carries only `source`; `PostToolUse` has no `success`/`is_interrupt`/`mcp_server`/byte counts (derived locally; `error`/`is_interrupt` live on `PostToolUseFailure`); `effort` is `{level}`; `PreCompact.custom_instructions` can be `null`; `SubagentStop` can lack `agent_id` (compaction summarizer); `SessionStart(source: compact|resume)` arrives for an existing session. `Notification` was not triggerable non-interactively.

### D7: OTLP/HTTP receiver inside the API, bearer-authenticated, protobuf and JSON
The API gains `POST /v1/otel/v1/metrics` and `POST /v1/otel/v1/logs` (the `/v1/otel` prefix exists so the single `/v1/telemetry|otel` HTTPRoute rule can bypass oauth2-proxy). It accepts `application/x-protobuf` (decoded with `opentelemetry-proto` generated classes) and `application/json` (OTLP/JSON), returns the OTLP success response, and never 4xxs on unknown metric/event names — unmapped records are counted and dropped. Mapped: `claude_code.token.usage` and `claude_code.cost.usage` (by `type`, `model`, `skill.name`, `plugin.name`, `agent.name`, `query_source`) → `usage_facts`; `claude_code.session.count`, `lines_of_code.count`, `commit.count`, `pull_request.count`, `active_time.total` → `usage_facts` with kind; log events `api_request` → `usage_facts` (per request, with `prompt.id`), `skill_activated` → `skill_activations`, `compaction` → `compactions`, `subagent_completed` → `subagent_runs` (upsert by `agent_id`), `tool_result`/`tool_decision` → enrich `tool_calls`, `api_error`/`api_refusal` → `turn_errors`, `hook_execution_*` → `hook_runs` (lets us measure our own hooks' latency), `user_prompt` (prompt_length only). Identity: the receiver requires the same `Telemetry.Write` bearer token as ingestion, supplied through `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer ...`; `python3 -m ouroboros_client.setup_otel` mints a **long-lived dev token** (default 90 days, scoped `Telemetry.Write`, `oid`/`upn` from env) and writes the OTel env block into `~/.claude/settings.json` (user scope — the docs say project/local settings are ignored for OTel). Entra later: tokens expire hourly, so the Entra phase adds a localhost forwarding proxy (`ouroboros otel-proxy`) that refreshes tokens; the receiver contract does not change. Alternatives rejected: a separate receiver image (third deployable, against the two-service constraint); an OTel Collector in-cluster forwarding to the API (extra moving part and config for a one-tenant system; revisit if we need fan-out to Grafana); unauthenticated receiver on a private path (anyone on the internet could inject cost data).

Spike result (0.2): proven end to end from Claude Code through the Envoy Gateway. The `Authorization` header set via `OTEL_EXPORTER_OTLP_HEADERS` reaches the pod intact under the route-level SecurityPolicy with `authorization.defaultAction: Allow` (the gateway ext-auth policy lists `authorization` in both `headersToExtAuth` and `headersToBackend`); a request without it gets our 401, not an oauth2-proxy redirect. **Route shape amended**: `/v1/otel` mounts as a second `PathPrefix` match on the existing `ouroboros-api` HTTPRoute, which already carries the own-auth SecurityPolicy, instead of a new route (D15, task 6.1); no new Gateway or ext-auth configuration is needed. **Client env**: `OTEL_EXPORTER_OTLP_ENDPOINT=<base>/v1/otel` suffices because Claude Code appends `/v1/metrics` and `/v1/logs` itself; no per-signal endpoint variables (task 2.5). **Decoding**: both `application/x-protobuf` and OTLP/JSON decode with the `opentelemetry-proto` classes (`ParseFromString` / `json_format.Parse(ignore_unknown_fields=True)`); `http/protobuf` is the documented default, and if tracing is ever enabled the JSON `traceId`/`spanId` (hex, where `json_format` expects base64) must be stripped before parsing. **Attribute-coercion layer added** before the mapping: the event name lives in `attributes["event.name"]` (fallback: the body string minus the `claude_code.` prefix; `LogRecord.event_name` is unset), integers arrive as strings (`intValue`), booleans as `boolValue` or the strings `"true"`/`"false"`, counters are delta sums as `asDouble`, and `cost_usd_micros` is preferred over the double `cost_usd`. **Mapping amendments**: `api_request` is the primary usage fact (D9); `plugin_loaded` and `hook_registered` feed the artifact registry (D10) as the per-session plugin/hook inventory (`plugin_id_hash` counts third-party plugins when names are redacted); `hook_execution_complete` → `hook_runs` with its `num_*` and `*_chars` counters; `assistant_response` → `response_length` only; `managed_settings_resolved` is counted and dropped; `anthropic.custom_base_url` is dropped, `user.id` is stored only as an opaque correlation hash, and the `prompt`/`response` attributes are never stored even though they arrive redacted. Identity remains the bearer JWT's `oid`/`upn`. The receiver logs one summary line per POST and counts records by `event.name`, which was enough to debug the whole flow.

### D8: Transcript ingestion is explicit opt-in, metadata-first, and gated on a spike
Transcripts (`~/.claude/projects/<project>/<session>.jsonl`, subagents under `<session>/subagents/`, big tool outputs under `tool-results/`) are the only source of per-message `usage` and `parentUuid` threading, but the line schema is undocumented. Ship `python3 -m ouroboros_client.transcript --session <id> [--content]` (and `--watch` for the current session): default mode uploads only `{uuid, parentUuid, timestamp, type, model, usage{...}, tool_use ids/names, content_length}` per line to `POST /v1/telemetry/transcripts`; `--content` includes message text (sensitive class) and requires a one-time acknowledgement stored in `~/.ouroboros/consent.json`. Never runs from a hook. Spike 0.1 inspects real files (main session, subagent, tool-results) and pins a parser with golden fixtures before any endpoint is built; the uploader refuses lines whose shape fails the fixture-derived schema instead of guessing. Alternatives rejected: automatic upload from `SessionEnd` (not explicit, pulls content by default, and the final message is not guaranteed in the transcript at `Stop`); reading transcripts server-side (they live on laptops).

Spike result (0.1): the on-disk structure is **stable enough to parse**. Every line is a self-contained JSON object discriminated by `type` (20 types in session files, 6 in subagent files; 0 malformed lines in ~20k across nine CLI versions); chain lines (`user`, `assistant`, `system`, `attachment`) carry `uuid`/`parentUuid`/`timestamp`/`sessionId`/`version`, `parentUuid` always resolves within the file, and `usage` is on every `assistant` line — but there is **one assistant line per content block** with identical `usage`, so usage is deduped by `message.id`. Helper-model spend (titles, classifiers) appears only in the end-of-session `cost-state` line, which is missing when a session does not end cleanly. Parser rules: order by chain, not timestamp (timestamps are not monotonic in file order); stream lines (12 MB files with inline base64 images); treat every non-envelope key as optional and record `version` on every extract; exclude `<project>/memory/*.md`. The default extract is one record per API message plus the `cost-state` session totals (identifiers and numbers only); `content_length` moves to the metadata-first extract. **Never uploaded in any mode**: `api-request-blob` lines (the full outgoing request, including the system prompt), `api-request` `tail`/`cacheControl`/`requestDigest`, `file-history-*`, `queue-operation` content, `frame-link`, `memory/`, thinking `signature` bytes and image data; `tool-results/` bodies are read only with `--content`. **Two assumptions remain unverified** and are explicit tasks (2.10, 2.11) that must close before transcript ingestion is relied on: (a) whether the final assistant message and its `usage` are flushed before the `Stop` hook runs (8/10 files end `assistant → system/turn_duration → … → cost-state`, so completeness at `SessionEnd` looks safe; `Stop`-time presence has to be tested from inside a hook); (b) whether the transcript `promptId` equals the hook `prompt_id` and the OTel `prompt.id` (same uuid v4 shape, equality untested; `user_prompt.message.uuid` is the fallback join). Default local retention is **30 days** (`cleanupPeriodDays`), so backfill windows are bounded to the sessions still on disk. Golden fixtures are **synthesized** from the structural reference with a length-preserving redactor; no real lines are committed (they carry account/organization UUIDs, paths and emails). Manual `/compact`, `type: summary`, non-`cli` entrypoints and `--resume` continuations are not in the corpus and need fixtures from 0.4.

Verified (2.10, 2.11): assumption (a) is **false at `Stop`** - in 2/2 runs the final `assistant` line (and its `usage`) was written only after the stop hooks returned - and **true at `SessionEnd`** (2/2, with `cost-state`); `system/turn_duration` is never written in `-p`/SDK sessions, and a new `system/stop_hook_summary` line follows the stop hooks. `transcript --watch` therefore reads a turn at the next `UserPromptSubmit` and the last turn at `SessionEnd`, never at the turn's own `Stop`. Assumption (b) is **true**: transcript `promptId` == hook `prompt_id` == OTel `prompt.id` (4/4 turns, incl. `/model` and `/compact`), and the fallbacks `user_prompt.message.uuid` == `user` line `uuid` and `assistant_response.message.uuid` == `assistant` line `uuid` also hold. Manual `/compact` and `--resume` fixtures now exist (`compactMetadata.trigger: "manual"`, `promptSource: sdk`).

Implemented (2.6, `client/ouroboros_client/transcript.py`, `api/app/transcripts.py`): the CLI is `transcript upload <path>` or `upload --session <id>`, `backfill --days N` and `consent` (prints the disclosure and records the acknowledgement that `--content` requires); `watch` is a stub that prints the read point above. Uploads go in batches of 500 and the endpoint applies no age limit (backfill is bounded by the local retention). `tool-results/` and `memory/` are never opened, in any mode: `--content` adds prompt and assistant text only.

### D11: Versioned SQL migrations applied by the API on start; indexes and retention by class
Replace `api/schema.sql` single-file application with `api/migrations/NNNN_<name>.sql` applied in order inside one transaction each, recorded in `schema_migrations(version, name, applied_at, checksum)`; `0001` is the current schema verbatim so existing databases converge; each file stays idempotent (`IF NOT EXISTS`) as today so a crashed apply reruns safely. The reporting service never migrates; it waits on `schema_migrations` reaching the version it was built for before reporting ready. Indexes: B-tree on every `(session_id)`, `(prompt_id)`, `(at)`/`(client_ts)`, `(skill_name, at)`; GIN on JSONB `payload`/`attrs`; a generated `tsvector` column with GIN on `turns.prompt_text`, `turns.response_text`, `events.feedback` text, for `websearch_to_tsquery` search replacing ILIKE. Retention by **sensitivity class**, enforced by a nightly job in the reporting scheduler (D13): `sensitive` text columns nulled after `RETENTION_SENSITIVE_DAYS` (default 30), `internal` rows (ids, hashes, artifact text) kept `RETENTION_INTERNAL_DAYS` (default 365), `public` aggregates kept indefinitely; `hook_events_raw` follows the sensitive clock since payloads may carry text. Alternatives rejected: Alembic (Python-model-driven migrations for a SQL-first schema add a dependency and a second source of truth); TimescaleDB (not in the CNPG image by default; plain partitioning is not needed at this volume).

### D12: Reporting auth trusts the Gateway header, roles from a small table, server-side redaction
The reporting service adds middleware: a request is authenticated iff it arrives from the Gateway/oauth2-proxy pod CIDR (`TRUSTED_PROXY_CIDRS`, the same pattern pgAdmin uses on this cluster) **and** carries `X-Auth-Request-Email`; anything else is 401, including direct in-cluster calls. `principals(email PK, role, created_at, created_by)` with `ADMIN_EMAILS` env as bootstrap (first admin, no secrets) and `/settings/users` for admins to add `leadership`/`engineer`/`admin`. Unknown emails get 403 (the Gateway allow-list is a second gate, not the authorization). Roles: `leadership` sees every aggregate and detail page but every `sensitive` field is replaced server-side by a length and a redaction marker; `engineer` sees verbatim text and can call the export endpoint; `admin` manages principals and approves proposals. Export: `GET /v1/export/{dataset}?from&to&format=ndjson|parquet` streams `turns`, `tool_calls`, `usage_facts`, `events`, `sessions`, `artifact_versions` with sensitive text included only for `engineer`+ and a `redact=1` option for sharing. Audit: every export and every proposal approval is logged to `audit_log`. Alternatives rejected: JWT validation of the oauth2-proxy id token (more correct but needs the issuer config in the reporting pod and buys little while traffic is CIDR-gated); client-side redaction (the data would already be on the wire).

Implemented (Phase 3, `reporting/app/auth.py`, `redaction.py`, `export.py`): the peer address is the ASGI socket peer (the Envoy proxy pod), never `X-Forwarded-For`, unless `TRUST_FORWARDED_FOR=1` (then the right-most hop); `/healthz`, `/readyz` and the SPA's static files stay public, `/v1/*` and `/internal/*` are gated; `ADMIN_EMAILS` are upserted into `principals` at startup (`created_by = 'bootstrap'`) and stay admin even if the row changes; `GET /v1/me` adds `landing` and `via`. Principal management is served at both `/v1/settings/users` (task 3.1) and `/v1/principals` (this spec); bootstrap admins cannot be changed through it (409). Redaction is one key-based layer (`RedactingRoute`) over every JSON response and per row in exports; the sensitive key set is `prompt_text`, `response_text`, `summary_text`, `input_content`, `output_content`, `title_redacted`/`session_title`, `content` (transcript lines), `message` (turn errors), feedback `notes`/`user_corrections`/`suggested_patch`, interaction `user_prompt`/`assistant_response`, and the raw hook payload text keys. Deviation: export is `engineer`+ only (leadership gets 403 rather than a redacted stream), per tasks 3.5; `redact=1` lets an engineer produce a shareable redacted file. `raw` projection copies and tsvector columns are never exported; `INTERNAL_REFRESH_TOKEN` (optional) lets an in-cluster CronJob call `POST /internal/refresh` without the Gateway identity.

### D13: Aggregations as materialized views refreshed by an in-process scheduler in reporting
Materialized views in a `analytics` schema, refreshed `CONCURRENTLY` by an asyncio ticker inside the reporting service (`AGGREGATE_REFRESH_SECONDS`, default 300; single replica, so no leader election yet; a Kubernetes CronJob calling `POST /internal/refresh` is the fallback if replicas > 1):
- `adoption_daily(day, skill_or_agent, kind, dau, sessions, turns, invocations)` and weekly rollup; retention = users active in week N and N+1.
- `outcomes_daily(day, skill_name, success, failure, user_corrected, correction_rate)`; `error_codes_daily`.
- `latency_daily(day, skill_name|tool_name, p50, p95, p99)` via `percentile_cont` over `events.latency_ms` and `tool_calls.duration_ms`.
- `cost_daily(day, model, skill_name, agent_name, input_tokens, output_tokens, cache_read, cache_create, cost_usd, sessions)`; per-session cost view.
- `context_bloat_daily(day, project_key, always_on_tokens, loaded_artifacts, compactions, mean_pre_tokens, bloat_index)` where **bloat_index = (always-on tokens of artifacts loaded at SessionStart / autoCompactWindow) + compactions per 100 turns × 0.5 + (mean pre_tokens / context window) × 0.5**, documented as a heuristic to be recalibrated once we have data.
- `sentiment_daily` (persisting what `/v1/reports/sentiment` computes in Python today) and `correction_themes(week, theme, count, example_event_ids)` from VADER-negative corrections + TF-IDF keyword clustering (scikit-learn is not added; a small stdlib tokenizer + the 50 most frequent bigrams per week is enough for v1). LLM theme scoring is a later optional job behind `THEMES_LLM=on`.
All series are bucketed on `client_ts`/`at` (event time), not `received_at`, so spooled uploads land on the day they happened. Alternatives rejected: computing on request in Python (today's approach; does not scale to hook volume and makes the UI slow); a separate analytics store (DuckDB/ClickHouse) — a third component for a one-tenant system.

Implemented (Phase 3, `reporting/app/scheduler.py`, `analytics.py`, `sentiment.py`, `themes.py`; migration `0010_scheduler_tables`): the ticker refreshes every `analytics.*` matview `CONCURRENTLY` when it is populated and has a unique index, falling back to a plain refresh for a `WITH NO DATA` view's first run. `sentiment_daily` and `correction_themes` became plain tables written by the scheduler in Python (the VADER half of the blend and the stop-word bigram clustering cannot be expressed in the 0008 matviews); a correction is "negative" when its blended score is below zero. Weekly (`bucket=week`) percentiles and bloat components are sample/session-weighted means of the daily view rows and are flagged `approximate`. Retention runs once per `RETENTION_INTERVAL_SECONDS` (86400): sensitive text is nulled (JSONB text keys stripped and marked `retention_redacted`) after `RETENTION_SENSITIVE_DAYS`, including `hook_events_raw.payload`, `transcript_lines.content` and the `raw` copies; after `RETENTION_INTERNAL_DAYS` the replayable/lifecycle stores (`hook_events_raw`, `transcript_lines`, `hook_runs`, `turn_errors`, `model_switches`) are deleted and `artifact_versions.content_text` of superseded versions is nulled. Fact tables the aggregates recompute from (`events`, `sessions`, `turns`, `tool_calls`, `usage_facts`, `skill_activations`, `compactions`, `instructions_loaded`) are kept, so "public aggregates kept indefinitely" holds across refreshes; each run writes one `audit_log` row (`retention.run`). Also added: `GET /v1/analytics/sentiment` over the persisted table.

### D14: Improvement loop v1 — analyst proposes, human approves, PR applies, outcomes measured
A scheduled **analyst job** in the reporting service (`ANALYST_SCHEDULE`, default weekly, also triggerable by admins) assembles an evidence pack per target artifact: its latest version text and token estimates, last-window aggregates (correction rate, failure rate, cost per invocation, always-on tokens, never-invoked status, compaction frequency when loaded), and up to N redacted-or-verbatim correction examples (verbatim only if `ANALYST_SEES_SENSITIVE=on`, default off). It calls Claude through the Claude API with a fixed prompt that must return a JSON proposal: `target_artifact_id`, `rationale`, `expected_effect` (tokens saved, correction-rate delta), `evidence_event_ids`, `unified_diff`, `risk_class` (`low` = description/when_to_use trims, `medium` = body edits, `high` = hooks/agents/CLAUDE.md semantics). Rows land in `improvement_proposals(proposal_id, target_artifact_id, base_version_id, rationale, expected_effect JSONB, evidence_event_ids UUID[], diff TEXT, risk_class, status proposed|approved|applied|rejected|superseded, created_by human|loop, created_at, decided_by, decided_at, pr_url)`. In the UI `/proposals` shows the diff and evidence; `admin` (or `engineer` for `low`) approves, which calls GitHub (installation token or fine-grained PAT held in a Kubernetes Secret, never in Git) to open a PR against the owning repo with the diff and a link back; merging is human. A webhook or poll marks `applied` with the merge SHA and version. `improvement_outcomes(proposal_id, before_window, after_window, metrics_before JSONB, metrics_after JSONB, verdict improved|neutral|worse|insufficient_data)` is filled by the scheduler once the after-window (default 14 days) has elapsed, comparing the same aggregate set the evidence pack used. Autonomy roadmap (not v1): auto-approve `low` risk once ≥N proposals of that class have verdict `improved` and none `worse`. Alternatives rejected: having the analyst edit files directly through an agent in CI (no approval gate, violates the stated v1 safety bar); storing proposals only as GitHub issues (loses the evidence join and outcome measurement).

Implemented (Phase 5, `reporting/app/analyst/{evidence,job,outcomes,patch}.py`, `proposals.py`, `github.py`; migration `0011_loop_states`): **Analyst** - disabled unless `ANTHROPIC_API_KEY` is set (`POST /v1/proposals/run` answers 503 with the reason, `GET /v1/proposals/status` and `/v1/me` `features` report `analyst: disabled`, the scheduler never starts it); `ANALYST_SCHEDULE` defaults to `""` (manual only; `daily`, `weekly`, `12h`, `7d` or seconds otherwise), `ANALYST_MAX_ARTIFACTS` 5, `ANALYST_MODEL` `claude-sonnet-5-5`, `ANALYST_EFFORT` `high`. Candidates are synced artifacts of a text kind with `owner_repo` and `path` and no open proposal, ranked by always-on tokens paid + weighted corrections/failures + a never-invoked bonus. One Messages API call per artifact: the fixed system prompt (`analyst/system_prompt.md`) is a cached block, the evidence pack (sorted JSON) follows it, `output_config.format` carries the JSON schema `{target{artifact_id,path}, rationale, expected_effect{tokens_saved,correction_rate_delta,summary}, evidence_ids, unified_diff, risk_class}`, adaptive thinking is left at the model default, and `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) is sent on models that support it. The answer is re-validated server-side (pydantic, `extra=forbid`); refusals, truncation, schema failures, a wrong target, an empty diff, a diff touching any path but the artifact's, or one that does not apply exactly to the stored `content_text` (no fuzz, `analyst/patch.py`) are discarded, logged and counted on the run. Evidence ids not in the pack are dropped. The service raises `risk_class` to a floor - `high` for hooks, agents, rules and instruction files, `medium` for any change outside the YAML frontmatter - so an engineer can approve only frontmatter/description trims. Each run is an `analyst_runs` row with token usage (input, output, cache read/write) and an `analyst.run` audit row; each proposal stores the metrics snapshot it was based on (`evidence` JSONB). **State machine**: `proposed → approved | rejected`, `approved → pr_opened | failed`, `pr_opened → applied | failed` (`superseded` reserved), each transition audited (`proposal.create|approve|reject|pr_opened|pr_skipped|failed|applied|outcome`). Rejecting is engineer+ for any risk; leadership reads with the rationale redacted when the analyst saw verbatim text. **GitHub**: a GitHub App (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, optional `GITHUB_APP_INSTALLATION_ID`, otherwise looked up per repo) mints installation tokens from a 9-minute RS256 JWT and caches them until expiry; `GITHUB_TOKEN` is the fallback; neither means approvals stay `approved` with "approved, PR creation not configured" and `POST /v1/proposals/{id}/open-pr` (admin) retries later. PR creation applies the stored diff to the file on the base branch (so a drifted base fails cleanly as `failed`), creates `ouroboros/proposal-<id8>`, commits through the contents API and opens a PR whose body links the proposal (`PUBLIC_BASE_URL`) and evidence events; the rationale is left out of the body when the analyst saw verbatim text. `POST /v1/proposals/github-webhook` is exempt from the Gateway identity check and authenticates with `X-Hub-Signature-256` over `GITHUB_WEBHOOK_SECRET` (503 when unset); merged → `applied` with `merge_sha`/`applied_at`, closed unmerged → `failed`; the scheduler polls `pr_opened` PRs every `GITHUB_POLL_SECONDS` (900) as the fallback. **Outcomes**: each tick fills `improvement_outcomes` for proposals applied ≥ `OUTCOME_WINDOW_DAYS` (14) ago with half-open `tstzrange` windows `[applied − W, applied)` and `[applied, applied + W)` and the evidence metric set; verdict `insufficient_data` when either window's sample (`max(invocations, sessions_loaded)`) is below `OUTCOME_MIN_SAMPLE` (20), otherwise rates compared by `OUTCOME_RATE_POINTS` (0.02 absolute) and always-on tokens / cost per invocation by `OUTCOME_RELATIVE_THRESHOLD` (10 %), with an invocation drop beyond the threshold counted as a regression; `improved` = some improved and none regressed, `worse` the reverse, else `neutral`. The API returns windows as `{from, to, days, bounds: "[)"}` (the dashboard's `TimeRange`); `/proposals/:id` shows the snapshots and verdict detail, `/overview` an "Improvement loop" card from `GET /v1/proposals/summary`. Deviations: status values gained `pr_opened` and `failed` (the original list had `approved` carry the PR URL); `evidence_event_ids` → `evidence_ids` in the model's schema (stored in the D14 column); outcome measurement is keyed on the merge time, not a synced post-merge version (`applied_version_id` is linked when one appears); auto-approval remains absent.

### D15: Deployment stays two images + CNPG; manifest deltas enumerated
No new deployables. Manifest changes in `deploy/apps/ouroboros` in this repo: a second `PathPrefix` match (`/v1/otel`) on the existing `ouroboros-api` HTTPRoute alongside `/v1/telemetry` (spike 0.2: that route already carries the own-auth SecurityPolicy, so both bypass oauth2-proxy with no new route or ext-auth config), request timeout raised to 30s and body limit to 8 MiB on those rules (OTel batches and spooled hook batches); API env `HOOK_EVENTS_MAX_AGE_SECONDS=604800`; reporting env `TRUSTED_PROXY_CIDRS`, `ADMIN_EMAILS`, `AGGREGATE_REFRESH_SECONDS`, `ANALYST_SCHEDULE`, `RETENTION_*`, and secrets `ANTHROPIC_API_KEY`, `GITHUB_TOKEN` via the cluster's existing secret mechanism; `ouroboros-db` storage from current size to 20 Gi with `resizeInUseVolumes`; CNPG `ScheduledBackup` to the cluster's object store becomes mandatory because the loop's proposals/approvals are not reproducible from clients; reporting `readinessProbe` waits for the migration version; an optional `CronJob` manifest for `/internal/refresh` kept but disabled. The reporting pod gets requests/limits bumped modestly for refresh work; the API stays as is. Alternatives rejected: a third `ouroboros/worker` image for scheduler + analyst (cleaner separation, but doubles the deploy surface for one tenant; split later if refresh work starves the API).

Landed so far in `deploy/apps/ouroboros` (`base/`, `routes/`, `overlays/rancherlocal/`): the `/v1/otel` match on the `ouroboros-api` route; a third route, `ouroboros-webhook`, for the exact path `/v1/proposals/github-webhook` under its own allow policy (D14); reporting env `AGGREGATE_REFRESH_SECONDS`, `RETENTION_SENSITIVE_DAYS`, `RETENTION_INTERNAL_DAYS` and `ANALYST_SCHEDULE` in the base, `TRUSTED_PROXY_CIDRS`, `ADMIN_EMAILS` and `PUBLIC_BASE_URL` in the overlay; optional Secret references `ouroboros-reporting-anthropic` (`ANTHROPIC_API_KEY`) and `ouroboros-reporting-github` (the GitHub App id, installation id, private key and webhook secret, in place of `GITHUB_TOKEN`). The OTLP receiver is always mounted, so there is no `OTEL_RECEIVER_ENABLED` switch, and `HOOK_EVENTS_MAX_AGE_SECONDS` and `ANALYST_SEES_SENSITIVE` are left at their code defaults. Still open (tasks 6.1-6.4): the route timeout and body limit, storage growth (the cluster is at 2 Gi) and the `ScheduledBackup`, readiness probe timing, and the CronJob manifest.

### D16: Client packaging — stdlib-only hook path, OTel needs no SDK, plugin versioning
The hook path (`plugin/scripts/ouroboros_hook_launcher.py` → `ouroboros_client.hook`) stays stdlib-only and network-free; the new projections add only `hashlib` for content hashes. `httpx` remains the only hard SDK dependency; `transcript` and `sync_artifacts` are plain stdlib + httpx. OTel requires nothing on the client beyond env: `python3 -m ouroboros_client.setup_otel` writes/updates the env block in `~/.claude/settings.json` idempotently and prints exactly what it enabled. The plugin bumps to `0.2.0` with `hooks.json` listing every new event with `async: true` and `timeout: 10`, and the plugin description plus `telemetry-reporting` SKILL.md disclosure are rewritten to list every collected class and every toggle (`OUROBOROS_TELEMETRY`, `OUROBOROS_CAPTURE_PROMPTS`, `OUROBOROS_CAPTURE_TOOL_CONTENT`, the OTel `OTEL_LOG_*` flags). SDK and plugin versions are reported in every hook event and OTel resource (`service.version`) so the server can gate parsers by version. Alternative rejected: a compiled single-binary hook (faster start, but Python 3 is already a requirement and the launcher's inert-fallback behaviour is specified).

### D17: Event time is `client_ts`; freshness relaxed for spooled structured data
Hook events and transcript lines keep the client's timestamp as the event time and the server records `received_at` separately; the 300 s freshness rule stays for `events` (outcomes should be near-real-time and the rule guards against replay) but `hook-events` and `transcripts` accept `client_ts` up to `HOOK_EVENTS_MAX_AGE_SECONDS` (default 7 days) so offline work is not dropped. Reporting filters and buckets on event time everywhere, fixing the `received_at` skew noted in the audit. Alternative rejected: one window for everything (either loses offline work or weakens replay protection on outcomes).

## Risks / Trade-offs

- [shadcn/ui is copied source, not a dependency] → upgrades are ours to apply, but each component is a single owned file (D1); `npx shadcn@latest diff` shows upstream drift.
- [Borrowed Tremor Raw files have no active upstream] → few in number, vendored in one directory with licence notice, each replaceable by a shadcn chart config (D3); spike 0.3 showed BarList ports trivially and DonutChart is not worth porting.
- [React 19 + Recharts 3 are newer than the current dashboard] → the dashboard is a rewrite, so no migration of existing views; pins verified in spike 0.3 (D3), no peer-dependency overrides needed.
- [Bundle grew from ~156 KB to ~335 KB gzipped in the spike] → route-level code splitting and a CI bundle budget (D3, task 4.14); Geist fonts optional.
- [shadcn on Base UI, not Radix] → one primitive library either way; the `render`-prop composition is the only API difference and blocks target Base UI (D1).
- [Claude Code hook/OTel schema drift] → whitelist projections tolerate unknown fields; raw JSONB kept for replay; parsers keyed on reported plugin/SDK version; unmapped OTel records counted, never rejected.
- [Hook volume raises per-turn cost] → async hooks, one small file write each; spool cap 5,000; batch upload off the hook path; measured in `hook_runs`.
- [Sensitive text now flows through more paths] → every content class is a named toggle, defaults chosen for minimum content; server-side redaction by role; retention nulling; disclosure updated before the plugin is released.
- [Long-lived dev token in settings.json for OTel] → 90-day expiry, `Telemetry.Write` only, user-local file, documented rotation; Entra phase replaces with the local proxy (D7).
- [Analyst proposals could be wrong or harmful] → human approval, PR review, risk classes, measured outcomes; `ANALYST_SEES_SENSITIVE` off by default.
- [Database growth and loss] → retention per class; CNPG backups mandatory; PVC resize.
- [Single reporting replica runs the scheduler] → acceptable today; `POST /internal/refresh` is the CronJob fallback (its manifest is task 6.4).

## Migration Plan

1. Phase 1 ships migrations `0001` (current schema) and `0002+` (new tables); existing rows untouched; reporting keeps working on `events`.
2. Phase 2 deploys the API with the new endpoints and the receiver; the old plugin keeps working (same `events` contract). Users upgrade the plugin and run `setup_otel` when they choose.
3. Phase 3 turns on reporting auth: the Gateway allow-list already limits who can reach it, so flipping to 401/403 for unknown emails is low risk; `ADMIN_EMAILS` bootstraps.
4. Phase 4 replaces the SPA; the old views live on under `/engineering` until parity.
5. Phase 5 enables the analyst with `ANALYST_SCHEDULE` set; proposals only.
Rollback at each phase is an Argo CD revert; migrations are additive (no drops in this change).
